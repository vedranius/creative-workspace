# Workspace-owned LightCraft browser preview (LGT-01a/01b)

Independent `cw-lightcraft-engine` embeds [LightCraft 0.6.0 by the ArtCraft team](https://github.com/storytold/lightcraft), pinned to `9e6c4c6f` by `manifest.json`. Upstream libraries and our original Rust worker are MIT OR Apache-2.0. This is a native worker, server gateway and browser preview at `/apps/lightcraft/`; dashboard still reports five available apps and labels LightCraft preview/planned. No desktop or MCP server starts.

Install: `npm run engine:lightcraft:install` (Rust 1.90+ and a native linker). Dedicated runtime/source paths use `CW_LIGHTCRAFT_RUNTIME` / `CW_LIGHTCRAFT_SOURCE`; the resulting worker is selected with `CW_LIGHTCRAFT_BINARY`. The installer retains pinned upstream dependencies and adds only the workspace package to Cargo.lock. CPU processing is selected explicitly; AI models, model downloads and optional craft-fonts are not enabled. The upstream missing-CJK-font build notice concerns optional text watermark support, which this worker does not expose.

Protocol: launch `cw-lightcraft-engine SOURCE_ROOT PRIVATE_OUTPUT_ROOT`; newline JSON `{id,method,params}` produces `{id,ok,result|error}`. Methods: `__cw_identity`, `controls`, `open {path}`, `state`, `set {values}`, `undo`, `redo`, `render/export {path,format?: png|jpeg,longEdge?}` and internal `mark_saved`. One photo/process; 128 MB source, 40 MP pixels, 4,096 px output edge, bounded 64 KB requests. Twelve native controls include exposure, contrast, highlights/shadows/whites/blacks, vibrance/saturation, texture/clarity/dehaze and sharpening. Render/export never clears dirty state. A future gateway must call `mark_saved` only after persisting editable settings at the selected destination and receiving its acknowledgement.

Upstream filesystem-backed hooks are intentionally not used. They can read entire files and `library.import` can also load adjacent XMP. Our bounded, canonical-root reader and original SHA-256 guard feed the engine's byte decoders directly. A single in-memory catalog photo is created from the probe; automatic XMP writing, external sidecar import, persistent catalog operations and arbitrary filesystem commands are excluded. Fresh decoder reads must match the originally opened hash; cached pixels represent that opened version. Outputs use a distinct private root and exclusive new files. Some RAW formats have only embedded-preview support upstream; those are explicitly refused rather than advertised as decoded RAW.

Validation on Linux: locked build, scoped shim fmt/clippy, two Rust safety/contract tests and `scripts/smoke-lightcraft-native.mjs`. The smoke creates a contributor-original 128×96 uncompressed Bayer DNG with no embedded JPEG, decodes/develops it, verifies changed preview pixels, undo/redo, JPEG export and fresh-worker JPEG reopen/PNG export. It confirms original/adjacent XMP preservation, rejected foreign read/write paths, rejected existing outputs/invalid controls and same-size changed-source rejection. No personal photos or external test media are used. This is not real-camera calibration/RAW-format coverage or browser/on-demand acceptance.

LGT-01b gateway and UI: `/api/lightcraft/sessions` accepts a server workspace, an explicitly selected allowed `sourceFolder`, or the common folder share; RPC supports photo/recipe open, 12 native controls, undo/redo, private previews, image export and editable recipe save. Recipes bind the confined relative source path, original SHA-256 and engine pin. `recipe.open` reads the recipe from the selected output/workspace root but resolves the original only beneath the explicitly selected source root and rejects changed bytes. Session version/dedup guards protect mutations. Only a recipe file acknowledged by server `receiveFile` or laptop exclusive write plus provider settle may call `mark_saved`; JPEG/PNG exports remain dirty. The browser preview is not listed as available and is not included in portable bundles.
