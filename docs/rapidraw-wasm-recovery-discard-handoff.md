The new app-recovery-discard variant opts into an origin-wide Web Locks journal protocol. Its output writes, receipt completion/automatic ACK retention cleanup and explicit removal share the lock. A busy lock refuses removal rather than waiting behind an active export. Timed-out operations report their deadline promptly while the lock remains held until all tracked late I/O and abort cleanup drains. A stuck mutation therefore prevents further coordinated mutation until it settles or the owning browser context ends; the UI does not report an acknowledgement or automatically retry.

Only records created with this coordination protocol can be removed. Older/uncoordinated records remain verifiable and copyable; removal is unavailable because an earlier writer does not participate in the lock. The completed app-file/app-export/app-recovery bootstraps retain their previous opt-out behavior and separate source contracts. This is cooperative same-origin journal coordination, not an atomic filesystem primitive for arbitrary external writers. Unsupported Web Locks fail closed before coordinated output I/O.

After the explicit confirmation, the session rechecks its inventory identity. Under the journal lock the backend rechecks the exact current metadata, bounded JPEG size/markers/SHA256 and metadata again before removeEntry. A changed entry or byte stream is refused. It returns discardAcknowledged only after removeEntry completes and a subsequent lookup yields NotFoundError. Failure or timeout cannot produce success. A late removal after a timeout is uncertain until an explicit inventory reload reconciles it; no automatic replay/delete follows. Session closure invalidates publication and checks before mutation.
