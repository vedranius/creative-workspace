# RWASM-03 — original export-preset persistence

This is an isolated native-source WASM experiment on `codex/rapidraw-wasm-port`. No product release, main integration, public demo or private photograph changed. The new browser storage behavior is complete within the scope below; it does not establish full App/settings/OS/common-provider acceptance.

[Actual browser evidence](evidence/rapidraw-wasm/settings-persistence-browser.json) · [Inspected screenshot](evidence/rapidraw-wasm/settings-persistence-browser.png).

The pinned native application calls `load_settings` in `useAppInitialization`, and `useSettingsStore.handleSettingsChange` calls `save_settings({settings})`. Native `app_settings.rs` resolves after serializing/writing `AppSettings` and configuring its cache. Those three contract files are independently hash-pinned in `UPSTREAM.json.settingsUi.nativeContract`. Native filesystem settings behavior is source-traced, not newly exercised here. No native renderer/WASM build or new pixel-parity claim is needed for browser preference storage.

The original React store was optimistic and swallowed errors; `ExportPresetsList` also closed create/delete and displayed Saved before its callback completed. The explicit [two-file ACK patch](../patches/rapidraw/b39884b3/settings-ack-v1.patch), SHA-256 `2c660a2d5fb8ce98579a0abb8d35b5612734771628a390a48b1c18ee3381a43e`, delays those changes until the original callback resolves, retains the form/previous preset on failure and displays a truthful reload-needed error. Layout, original preset algorithms, command IDs, rendering and export code remain source-based. The original26 baseline source pins are retained; two applied source files have separately recorded patched hashes. Do not describe the patched files as byte-identical originals.

`settings-storage.js` accepts a bounded preview-settings/JPEG-preset slice: at most64KiB serialized settings and32 presets, bounded IDs/names/numbers, explicit supported fields. These are accepted-data bounds, not a pre-allocation or physical-memory guarantee. It never persists last export paths, watermark paths, subfolders, handles or chooser leases; restored destinations require a fresh custom-folder choice. Unsupported top-level path/AI/sidecar settings refuse. `save_settings` is independent of preview/GPU queues and resolves only after an IndexedDB readwrite transaction commits and readback exactly matches its revision/payload. Revision CAS refuses stale writers. Storage errors, mismatches and10s deadlines leave the host uncertain and refuse further saves until explicit reload/reconciliation; pending late IO prevents a new operation. Corrupt data is preserved, never reset or replayed automatically.

Sandboxed Chromium loads the public hash-pinned CC0 Canon A410 DNG through the existing unchanged RAW/WASM/render path and exercises actual original controls:

- Create “Travel JPEG”: quality60, long edge1200, DPI144. A real committed revision1 is held at readback; the UI remains revision0, with no preset and the create form still open until ACK.
- Overwrite quality95: the source store retains60 and displays no Saved badge until matching revision2 readback. After reload the original dropdown applies quality95/DPI144. RAW selection is null until a new explicit file choice; no opaque output/document URI restores.
- Inject an actual abort into the IndexedDB write transaction: revision2 and the old preset survive in storage/UI; the form retains “Must not persist” and reports failure. No automatic retry follows.
- Corrupt-record control: a real QA record with schema2/revision3 is preserved when the old loaded writer attempts a save; the transaction aborts without resetting or overwriting it.
- Delete: the source list retains its preset until readback ACK3, then reload confirms deletion. A separately loaded stale host cannot write revision2 over3; its real IDB transaction aborts and the stored empty list remains.

Three readback ACK gates pass. No page/network/external-request errors; one expected settings-save error from the injected abort. The existing unsupported `get_lensfun_makers` command logs on four fresh source mounts remain explicitly unimplemented.
