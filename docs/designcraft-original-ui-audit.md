# PAR-01 — DesignCraft original UI source audit

Audit date: 2026-10-11. Source checkout: `/home/vedran/Documents/Codex/2026-10-10/da-x20/work/designcraft`, pinned at `a127c6d5` (working tree clean at audit). This is a source audit, not a product acceptance or availability claim.

## Finding

The pinned upstream already contains `apps/designcraft-web`, an eframe `WebRunner` shell that constructs the same `designcraft_ui_egui::DesignApp` as the native application. This is a viable source-based path to the original DesignCraft UI. It is not the desired server-processed product today: the web shell creates `designcraft_engine::Session::new()` in WASM, and the application performs document commands and canvas rendering in the browser. The source also says web saves/exports trigger browser downloads, and its `Services` implementation uses an asynchronous browser file picker and an in-memory inbox. So the genuine UI path exists, but the server-processing requirement is not met.

## Source evidence

- `apps/designcraft-web/Cargo.toml` depends on `designcraft-ui-egui` and `designcraft-engine`; its WASM-only dependencies are eframe/WGPU, `rfd`, wasm-bindgen and browser APIs. `index.html` launches that Rust/WASM binary on a canvas; `web.rs` starts `eframe::WebRunner` and wraps the original `DesignApp` (`apps/designcraft-web/src/web.rs:33-65, 80-115`).
- The native application also constructs `DesignApp` from `designcraft-ui-egui` (`apps/designcraft/src/main.rs:20-21, 292-333`). The UI crate owns the menus, dialogs, panels, toolbar and canvas; `menus::menu_tree`, `menus::shortcuts`, dialog dispatch and `toolbar.rs` consume shared source registries. The tool catalogue defines 27 tool entries across its groups (`crates/tools/src/catalog.rs:10-78`); menus and parameter dialogs are generated/dispatched from the shared UI/engine command metadata (`crates/ui-egui/src/menus.rs:8-60, 1720-1840`). This is a real shared-UI entry point rather than a reimplementation in browser HTML.
- `DesignApp` owns a concrete `Session`; its host `Services` are callbacks for file read/write/pickers, with async imports delivered by inbox (`crates/ui-egui/src/lib.rs:38-74, 444-500`). In `apps/designcraft-web/src/web.rs:118-149`, file selection reads bytes into that inbox, `pick_save` returns a suggested name, and `write`/`download` invoke a browser download. This does not provide server workspace roots, FSA permissions, provider selection or destination-write acknowledgement.
- The engine exposes a synchronous mutable command boundary, `Session::execute(&mut self, id, params)`, plus session/document state and command metadata (`crates/engine/src/lib.rs:247-280, 389-425, 520-535`). The original pointer tools and UI call into this in-process session; a server-owned session cannot be substituted by changing only the browser file callbacks.
- Canvas rendering is also local in the current WASM build: `CanvasCache` owns a `designcraft_render::Renderer`; its background worker is compiled only for non-WASM, while the WASM branch defines an empty `Worker` (`crates/ui-egui/src/lib.rs:380-435`, `crates/ui-egui/src/render_worker.rs:1-8, 72-73`). The UI performs rendering synchronously on the browser's render path.
- The native entry point has OS-specific facilities: native menus (`muda` on macOS), local config/recovery, native file dialogs, a localhost control server and native GPU startup selection (`apps/designcraft/Cargo.toml`, `apps/designcraft/src/main.rs:185-210, 231-333`). The separate web binary omits these native bootstrap modules and substitutes browser services. They are host integrations, not reasons to replace the shared UI. Whether the complete wasm target still builds on this machine was not tested: only `x86_64-unknown-linux-gnu` is installed and `trunk` is unavailable.

## Minimum next implementation task

Port the pinned `apps/designcraft-web` and shared `designcraft-ui-egui` source into an isolated Creative Workspace build unchanged first; do not extend the current custom DesignCraft page as the target UI. Add a server-owned DesignCraft session adapter and a narrow, versioned RPC boundary that the original UI can call for commands, session snapshots and render results. Keep the server as sole owner of `Session`; bind every request to authenticated Origin, user/session and an explicitly chosen provider root. Bound command payloads, source bytes and render dimensions. Represent browser-selected files as opaque, granted handles/server upload IDs rather than trusting paths. For laptop reads, request only selected files. Save/export must target the user's chosen provider and report success only after that provider acknowledges the write; preserve uncertain output for recovery. Keep upstream menu/tool/dialog/action registries in the shared UI crate and map their existing command IDs to server execution rather than rebuilding a limited tool list.

### Smallest proof of feasibility

1. Build the pinned web app and serve it from an isolated temporary port. In a real browser, verify the original menu bar, representative original dialog, toolbar/tool groups and canvas render. Record the source revision, browser and screenshot. This proves UI source reuse only.
2. Wire one non-destructive representative action and one bounded document snapshot/render request through an authenticated, Origin-checked RPC to an owned server worker with a server-owned `Session`. Verify worker logs/counters establish that command and document rendering ran server-side while the original browser UI remains active.
3. Only after that slice works, add selected-source open and a new-name save/export using provider roots and destination ACK. Verify the exact source bytes, no unrelated reads, destination acknowledgement, reopen, and session/root isolation. Do not call step 1 alone a server-processing proof or mark the adapter available.

The first code task should be the smallest seam needed to replace direct `Session::execute`/canvas-render ownership in the UI while preserving source menus, tools, dialogs and pointer workflows. Before choosing a message protocol, trace every UI read of `Session`/`DocState` and every command/tool execution in `crates/ui-egui`; do not assume that moving only `execute` is sufficient. Keep the existing browser-download shell and Creative Workspace prototypes as development artifacts until the server-backed path is proven.
