# Original DesignCraft footnote contract — diagnosed, not accepted

The generated three-page facing document exposes a different address type from ordinary table cells. Original `CellAddr::footnote(id)` uses `FOOTNOTE_TABLE = u64::MAX`, row=note ID and col=0. It is not table0 and must not be interpreted as an ordinary table cell. Native Rust serializes the sentinel exactly as `18446744073709551615`. JavaScript `JSON.parse` converts it to an unsafe Number; `JSON.stringify` emits `18446744073709552000`. The original UI's `serde_json::from_value::<Selection>` cannot hydrate that rounded value as u64. Allowing a larger table ID in the existing cell guard would preserve the loss and would not repair the ACK.

Source is pinned to DesignCraft `a127c6d5c3576972bbd60445f26d893db071eef3`, reviewed integration patch `be3a5117dafe43b9212e2e3771541c444284a5d9e0a0b221162d199d15253b22`. Relevant original code:

- `crates/doc/src/selection.rs`: `CellAddr::footnote` and `footnote_id`; `crates/doc/src/notes.rs`: reserved `FOOTNOTE_TABLE` sentinel.
- `crates/compose/src/notes.rs`: `find_note`, `hit_note` and `note_caret`. Caret already adds the placed note origin; it must not be added twice by the adapter.
- `crates/ui-egui/src/canvas.rs`: `draw_cell_selection` handles notes by `find_note`/its composed text, uses the same translucent blue quads as cells and the original black blinking caret. Range geometry needs note origin before frame/ancestor transforms; caret geometry needs only the latter because compose has already added origin.
- `crates/engine/src/cmd/notes.rs`: original `footnote.insert`, list, setText, delete and goToReference. The existing original text hit/select/insert commands operate on note text when the selection has the reserved address.
- Patched `crates/ui-egui/src/lib.rs`: `apply_host_action_ack` deserializes acknowledged selection before committing the mirror/revision. This correctly refuses malformed selection instead of claiming success.
